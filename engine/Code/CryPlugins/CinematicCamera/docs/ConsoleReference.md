# CinematicCamera Console ReferenceConsole commands registered by the plugin, plus the renderer cvars the Cinematic Camera systemrelies on (registered in `Code/CryEngine/RenderDll/Common/RendererCVars.cpp`).The cvars fall into two groups:- **Live tuning (character)**: values used in normal operation. Note that  `r_HDRVignetteAmount`, `r_LensDistortion`, `r_LensChromaticAberration` and `r_LensLetterbox`  are **overwritten every  frame** while a cinematic camera drives the render state (from its Vignette / Distortion /  Anamorphic Squeeze properties), so  setting them by hand only sticks while no cinematic camera is active; the plugin restores  the pre-activation values when the camera stops driving.- **Diagnostic**: force modes used to verify that a pipeline stage runs at all, independent of  what the game code feeds it.Naming standard: every depth-of-field cvar spells the family out as `r_DepthOfField*`. Threecvars were renamed to follow it:| Old name | Current name || --- | --- || `r_DofBokehShapeStrength` | `r_DepthOfFieldBokehShapeStrength` || `r_DofSpriteBokehDebug` | `r_DepthOfFieldSpriteBokehDebug` || `r_DofResolutionScale` | `r_DepthOfFieldResolutionScale` |(The C++ members keep their short `CV_r_Dof*` names; only the console-facing names changed.)## Console commands### ccam_slot```ccam_slot <1-9>```Activates the cinematic camera whose **Camera Slot** property equals the given number, whichis the same ownership transfer as the Schematyc `Activate` function. It logs the entity itswitched to (`[CinematicCamera] slot 3 -> 'CamB'`) or reports that no cinematic camera carriesthat slot. Called with no argument it prints its usage line.A Phone Tracker with **Follow Active Camera** enabled follows every switch, re-anchoring onthe new camera and re-sending the last lens state to it.Bind the slots to the number keys to cut between cameras during play:```bind 1 ccam_slot 1bind 2 ccam_slot 2bind 3 ccam_slot 3```The same switch is exported for other plugins as `CryActivateCinematicCameraSlot(int slot)`(see `Interface/ICinematicCameraOptics.h`).### rec_CaptureEXR / rec_CaptureEXRStop / rec_CaptureEXRFrame```rec_CaptureEXR [folder] [prefix]rec_CaptureEXRStoprec_CaptureEXRFrame [name] [folder]```Write the scene-referred frame to OpenEXR - half float, ACES primaries, with the camera's ownsettings in the header. `rec_CaptureEXR` starts a sequence and runs until `rec_CaptureEXRStop`;`rec_CaptureEXRFrame` writes exactly one and disarms.Relative folders land under the user folder, absolute paths are taken as given, and the folder iscreated if it does not exist (default `CaptureEXR`). Files are `<prefix>.%06d.exr` (default prefix`frame`) - dot-separated, which is what Nuke and Resolve auto-detect as a sequence. The framecounter belongs to the capture and starts at zero on every arm; it is **not** `capture_frames`,which `ManualFrameStep` and CryMovie also write, and none of the stock capture path is touched.`rec_CaptureEXRFrame` differs in two ways, both because a single frame is not a sequence. Itsarguments are **name first, folder second** - what you want to say about one frame is what it is,not where it goes - and its **numbering continues for the whole session**: it uses the first free`<name>.%06d.exr` in that destination, so repeated captures are consecutive and nothing already ondisk is overwritten. Delete a file and its number is reused.Nothing is written unless the camera's **Scene Referred** path is running - off it there is nopre-ODT buffer to tap.A **sequence** sets `t_FixedStep` (see `r_SceneReferredExportFixedStep`) and freezes the lensmodel's jitter phase (`r_DepthOfFieldLensModelJitter 2`) for its duration, restoring both on stop.A single frame leaves them alone. If the readback or the disk falls behind, the capture stops andsays so rather than dropping a frame.What is written is decided by the four `r_SceneReferredExport*` cvars below, all latched at themoment the capture starts.
