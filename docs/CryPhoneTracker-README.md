# CryPhoneTrackerA native CRYENGINE 5.7 plugin providing the **Phone Tracker** entity component (Sandboxcategory: **Tracking / Phone Tracker**): it receives packets from the Android ARCore phonetracker (`cryengine-57-lts/androidtracker`), drives an entity's position and rotation from the6DoF pose, and forwards the lens faders on the phone (focal length / aperture / focus / ISO /EV) to a **Cinematic Camera** component.## Connection- The component opens a **UDP** socket when entering game/simulation mode (`Listen Port`,  default 9050), non-blocking, drained empty every frame, so the entity always follows the  newest pose instead of a backlog. In pure edit mode the entity receives no Update event and  does not move ??that is engine behaviour.- In the phone app's Settings, enter the PC's LAN IP and the same port, transport UDP.- Control packets (Recenter, AF results) are sent back through the same socket to the address  the last packet came from.- **Port conflicts are named.** Two trackers on one port would silently fight over the bind  (and the loser would get no packets and no error), so before binding, the component looks  for another live tracker on the same port and refuses with  `PORT 9050 BUSY - held by tracker #2 'CamRig'` ??shown both as a warning in the log and in  the debug overlay. A port taken outside the level reports  `PORT 9050 BIND FAILED - in use outside this level (another process?)`.### Tracker ID**Tracker ID** (Connection group, 0-99, default 0) is the number this tracker answers to inlogs and in the debug overlay, so several trackers can be told apart. `0` means automatic:the tracker's position in creation order, 1-based. Every log line and the overlay carry it(`[PhoneTracker] #1 'PhoneCam': listening for pose packets on UDP port 9050`).## Following the active cinematic camera**Follow Active Camera** (Transform Mapping, default on) makes the tracker drive whicheverCinematic Camera is currently active instead of its own entity ??so the phone becomes theoperator of whatever camera the console command `ccam_slot N` (or a Schematyc `Activate`)selected. The active camera entity is resolved through the C entry point`CryGetActiveCinematicCameraEntity()` exported by `CinematicCamera.dll`.On every switch:- The tracker **re-anchors** on the new camera: its reference transform is re-captured from  where that camera was placed, and the next pose re-captures the tracker origin against it  (the recenter path), so the phone carries on from wherever the new camera sits instead of  teleporting it. The phone's own frame is left alone ??no control packet is sent.- The pose filter is reset, so no transient from the previous camera carries over.- The **lens link follows too**: the new camera's optics are resolved and immediately handed  the lens state the phone last sent, so the cut does not land on stale lens values.- The switch is logged: `[PhoneTracker] #1 'PhoneCam': controller now drives 'CamB'`.When no cinematic camera is active (or the CinematicCamera plugin is not loaded), the trackerfalls back to driving its own entity.## Coordinates and Transform MappingARCore and CRYENGINE are both right handed, so only an axis swap is needed: position`(x, y, z)` -> `(x, -z, y)`, quaternion `(qx, qy, qz, qw)` -> `(qx, -qz, qy, qw)` (matching`tools/pose_monitor.py`).Pose pipeline order: **PoseFilter (tracker space, metres) -> MapToWorld (origin / yaw / scale /offset) -> optional legacy smoothing -> written to the entity**. All thresholds operate inphysical units and are unaffected by `Metres To Units`.**Align Yaw On Start** (default on): anchoring uses only the yaw of the starting poses (phoneand entity alike); pitch and roll stay gravity aligned, so turning the phone always rotates theentity around the world up axis. With it off, a phone tilted at capture time tilts the wholerotation frame. With the phone looking straight up or down the heading is taken from the upaxis instead, so it never degenerates.Recenter (the Schematyc function, or the phone recentering itself ??the incrementing`originEpoch` is followed automatically) takes the **filtered** pose as the new origin (sojitter is never frozen into it) and re-captures the current target transform as the reference,so recentering never teleports the entity.## PoseFilter pipeline`Module/PoseFilter.h`, header-only, no `gEnv`, no dynamic allocation, unit-testable outside theengine. Four stages:| Stage | Runs | Contents || --- | --- | --- || A clock rebasing | per packet | Maps phone frame timestamps onto the engine clock: an EMA absorbs drift (at most 2 ms correction per packet); a deviation over 200 ms is treated as a phone clock jump and resets the set. || B One Euro | per packet | Position uses one cutoff for all three axes (`posMinCutoff + posBeta * speed`); rotation takes the shortest arc with an angular-rate adaptive cutoff. || B' fixed delay resampling | per render frame | 16-slot ring buffer sampled `packet interval * Resample Delay` behind the engine clock: cubic Hermite for position (tangents from the filtered velocity), slerp for rotation. During a signal gap the pose is extrapolated for at most `Max Extrapolation` ms (velocity decaying linearly), then frozen on the last pose ??never snapping back. || C virtual tripod | per render frame | See below; Cinematic mode only. |### Pose Filter properties| Property | Range | Default | Description || --- | --- | --- | --- || Filter Mode | Off / One Euro / Cinematic | Cinematic | Off reproduces the unfiltered path exactly; One Euro = stages A+B+B'; Cinematic adds the virtual tripod. || Position Min Cutoff | 0-10 Hz (slider 0-5) | 1.0 | Lower values kill more jitter while the camera is still. || Position Speed Coefficient | 0-5 per m/s (slider 0-2) | 0.5 | How fast the position cutoff opens up with speed. Raise it if fast moves feel laggy. || Rotation Min Cutoff | 0-10 Hz (slider 0-5) | 1.2 | Rotational jitter suppression while still. || Rotation Speed Coefficient | 0-5 per rad/s (slider 0-2) | 0.1 | How fast the rotation cutoff opens up with angular rate. || Resample Delay | 1-4 | 1.5 | Packet intervals of buffering used to hide network jitter. Higher is smoother but adds latency. || Max Extrapolation | 0-80 ms | 0 | Milliseconds the pose may be extrapolated into a signal gap. 0 freezes on the last pose. |## Virtual TripodOnce the operator holds still the pose locks completely, so composing a shot is rock steady.State machine: **Moving -> Arming -> (after Hold Time of stillness) Steady -> (movement)Blending -> Moving**.- Entry: speed below `Tripod Enter Speed` and angular rate below 0.8 deg/s (fixed constant).- While Steady the anchor tracks ARCore's long-term drift at 0.1 Hz, but stays **bit-exact**  inside a 0.5 mm / 0.02 degree dead band ??a phone on a table really does hold the transform  perfectly still.- Release: further than `Tripod Release Distance` from the anchor, or more than 0.5 degrees of  rotation, or faster than 0.05 m/s (the latter two are fixed constants). Release blends back  to the live pose over `Tripod Release Blend` seconds with a smoothstep; going still again  mid-blend re-locks in place with no visible jump.| Property | Range | Default | Description || --- | --- | --- | --- || Virtual Tripod | bool | true | Master switch (Cinematic mode only). || Tripod Enter Speed | 0-1 m/s | 0.015 | Metres per second below which the tripod starts arming. || Tripod Hold Time | 0-2 s (slider 0-1) | 0.25 | Seconds of stillness required before the pose locks. || Tripod Release Distance | 0-1 m | 0.01 | Metres of movement away from the locked pose that releases the tripod. || Tripod Release Blend | 0-2 s (slider 0-1) | 0.15 | Seconds spent blending from the locked pose back to the live pose. |## Other properties### Connection| Property | Range | Default | Description || --- | --- | --- | --- || Enabled | bool | true | Open the socket and drive the entity while in game/simulation mode. || Listen Port | 1-65535 (slider 1024-65535) | 9050 | UDP port the phone sends pose packets to. || Tracker ID | 0-99 | 0 | Number shown in logs and the debug overlay so multiple trackers can be told apart. 0 = automatic (order of creation). |### Transform Mapping| Property | Range | Default | Description || --- | --- | --- | --- || Follow Active Camera | bool | true | Drive whichever Cinematic Camera is currently active (switch with `ccam_slot N`) instead of this entity. On the PCside a ray is cast along the camera axis from 0.3 m in front of the driven entity out to500 m (static / terrain / rigid); the hit distance becomes the focus distance, and with no hitthe focus racks to infinity (10000 m). The DOF user params are eased by the renderer itself(~0.3 s time constant), so the rack glides like a real AF drive. The result is reported backwith a `SetFocus` control packet (param = distance in millimetres) so the phone's focus faderfollows and the later 4 Hz lens resends carry it.## Debug overlay (Debug Draw)One block per tracker, stacked by creation order so several overlays never overlap.- Line 1: `Tracker #N 'entity' :port  from IP  -> 'target'  TRACKING/NO SIGNAL  packets N  loss %  state N  battery %  app N fps`. `#N` is the Tracker ID, `'entity'` the component's  own entity, `IP` the sender address of the last packet (`no phone yet` before the first  one), and `'target'` the entity currently driven ??the active cinematic camera when  following.- When the socket is closed the line collapses to `Tracker #N 'entity' :port  <problem>`,  where the problem is the port conflict message, `SOCKET CLOSED`, or `DISABLED`.- Line 2: the position currently written, `pos (x, y, z)`.- Line 3 (filtering enabled): filter mode, tripod state (MOVING / ARMING / STEADY / BLEND) and  blend %, speed m/s, angular rate deg/s, effective cutoffs (pos/rot Hz), buffer depth,  resample delay ms, and an `EXTRAPOLATING` marker.- Line 4 (once a lens packet has arrived): focal mm, f-number, focus m, EV, ISO, plus a  `(no Cinematic Camera)` note when no optics could be resolved.## Protocol (`Module/PhoneTrackerProtocol.h`)Matches the phone's `net/PacketCodec.kt` and the verification tool `tools/pose_monitor.py`;everything little endian over the same UDP socket, `version = 1`.| Packet | Direction | Size | Magic || --- | --- | --- | --- || Pose | phone -> PC | 64 bytes | `0x54443350` ('P3DT') || Lens | phone -> PC | 32 bytes | `0x534E4C50` ('PLNS') || Control | PC -> phone | 28 bytes | `0x54433350` ('P3CT') |**Pose (64B)**: magic, version, flags, seq, originEpoch, deviceNs, frameNs, position px/py/pz(ARCore right handed, Y up, metres), quaternion qx/qy/qz/qw, trackingState, failureReason,batteryPct, appFps. Pick an entity -> Add Component -> **Cameras / Cinematic Camera**, then Add Component ->   **Tracking / Phone Tracker**.2. In the phone app enter the PC's LAN IP and a port matching `Listen Port` (default 9050),   transport UDP.3. Enter Game Mode (Ctrl+G) or Simulation; the component opens the socket and starts updating   the entity.4. Press **Lens** on the phone to open the fader panel; press **RECENTER** to reset the origin.5. Turn on `Debug Draw` to watch the connection and filter state.6. With **Follow Active Camera** on, place several Cinematic Cameras, give each one a Camera   Slot, and cut between them with `ccam_slot N` (bind it to the number keys) ??the phone takes   over whichever camera is active.
