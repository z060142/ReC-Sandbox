# CinematicCameraA physically based camera component driven by real lens parameters (Sandbox category:**Cameras / Cinematic Camera**):- **FOV** from focal length + sensor size, written into the sibling `CCameraComponent` the  component creates automatically (so the entity shows up in Sandbox's Camera Entity menu and  the editor viewport previews it with the correct frustum).- **DOF** from aperture + focus distance through the thin-lens equations, written to the  `Dof_User_*` post effect params.- **Exposure** written to `E3DPARAM_HDR_EYEADAPTATION_PARAMS` from the plugin's  `UpdateBeforeFinalizeCamera()` hook (after the Time of Day update, so TOD cannot overwrite  it in the same frame).- Also drives **Film Grain**, **Motion Blur**, **White Balance**, **lens character**  (vignette / distortion), **Diffraction Streaks** (sunstars), **Halation** (the red-orange  film halo), the **Front Filter** point spread function (star filters) and the hybrid  **sprite bokeh** highlight splats.Lens values can be pushed live from a phone fader panel by[CryPhoneTracker](../CryPhoneTracker/README.md); the interface is`Interface/ICinematicCameraOptics.h` (`CinematicCamera.dll` exports`CryGetCinematicCameraOptics(IEntity*)`).Schematyc functions: `Activate`, `Deactivate`, `IsActive`.---## Camera slots and switchingEvery cinematic camera can carry a **Camera Slot** number (1-9, `0` = no slot, the default).The console command```ccam_slot 3```activates the cinematic camera whose Camera Slot is 3, and logs the entity it switched to(or a message when no camera carries that slot). Bind the slots to the number keys to cutbetween cameras while the game runs:```bind 1 ccam_slot 1bind 2 ccam_slot 2bind 3 ccam_slot 3```A Phone Tracker with **Follow Active Camera** enabled moves along with each cut, re-anchoringon the new camera. See [docs/ConsoleReference.md](docs/ConsoleReference.md) for the commandreference.The same switch is available to other plugins as the exported C entry points`CryActivateCinematicCameraSlot(int slot)` and `CryGetActiveCinematicCameraEntity()`.## Single authority: who owns the render stateThe **camera manager decides** which camera is active; the component only caches its answer.Once per frame the plugin hook calls the resolver, which walks the registry of live cinematiccameras, finds the one the manager considers active, and ??when the answer changed ??makesthe dethroned component restore every render state it had taken over. Only theresolver-confirmed active component may write DOF, grain, motion blur, white balance,streaks, sprite bokeh, vignette/distortion or exposure; components in a Preview simulation(asset browser preview windows) never write them at all.`Activate()` activates the sibling `CCameraComponent`, which IS the ownership transfer.`Deactivate()` does **not** null the manager's active camera ??the engine always needs someactive view. Its meaning is: strip this component's cinematic effects (full restore sweep)and mark it suspended, so the entity stays a plain view until another camera activates.`IsActive()` reports false while suspended, and `Activate()` clears the suspension.**Activate On Game Start** must stay opt-in: every component receives START_GAME, so withseveral cinematic cameras in a level the last one to get the event would silently steal theview from an explicit Schematyc `Activate` call.## Edit mode policyEffects split by whether they depend on the view:| Effect | Editor (edit mode) | Game / simulation mode || --- | --- | --- || Depth of field, sprite bokeh, motion blur, film grain, white balance, diffraction streaks | not applied | applied || Vignette, distortion (lens character) | live | applied || Exposure | live | applied |In edit mode the viewport renders through the editor fly camera, so pushing this camera'sfocus and blur onto it would produce meaningless imagery. View-independent character stayslive so it can be authored with immediate feedback.Entering game/simulation mode drops every saved baseline without writing anything (theeditor's `ResetPostEffects()` has already wiped the renderer, so the captured values arestale); leaving it runs the full restore sweep. Everything a sunstar does follows from that, andthe camera offers two models of it ??`Streak Model`, exclusive, defaulting to Wave.### Wave optics (default)The renderer rasters the **on-axis pupil** on a 512x512 complex grid ??the iris polygon (thesame `NGon_Rad` outline and the same curvature-derived exponent the bokeh uses), intersectedwith the shape mask at the mask's own rotation and scale, intersected with the barrel ??andgives it a phase: spherical aberration is a **wavefront error**, `W = k_sa * 0.25 waves * r^4`,which is the physically right place for it and is what puts rings and a halo around the rays.An FFT of that is the point spread function. The **core is removed** (the frame already carriesthe source and its bloom) and the frame's thresholded highlights are convolved with what isleft ??one sprite per bright **half-resolution** texel, the front filter's sparse convolution runone resolution finer and deposited into a **layer of its own**, which is added to the frame afterthe bloom stage (where the lens ghosts are added, and for the same reason: every glare thresholdhas already been taken, so the pattern cannot halate or streak off itself). The thresholdedsource is given a small Gaussian pre-blur first ??physically the convolution of the pattern withthe source's own extent, practically what stops a lamp's block of bright texels from summing intoa pattern with a **square** core. Quarter resolution did both of those things wrong: the sourceblock was 3x3 and the deposit was magnified 4x onto the pattern's steepest slope, which is whatput visible blocks around every source. The pattern is scaled to the pupil's whole transmitted light *before* the corecomes out and is never renormalised afterwards, so **`Streak Amount` 1 deposits exactly thephysical fraction** ??of which only about **0.5 % of the source** reaches the rays proper,some `1e-5` of the source per pixel twenty pixels out. Real sunstars are visible only becausethe sun or a night streetlight is `1e4`?1e6`? the scene, while a game light's HDR value isclamped to a few tens; so **`Streak Amount` is a source radiance boost** ??how much brighterthe true source is than that clamped value ??with **50** as the default and 10??00 the usefulrange (entities saved before that default changed keep their saved value). It scales thesource, never the pattern: shape and falloff stay physical throughout.**Under Scene Referred the sources are no longer clamped, and the amount becomes gain in stops.**Ten units of the slider is one stop; the shipped 50 sits on the physical 1.0, so 100 is +5 stops,150 is +10 and 200 is +15. That range is not generosity, it is what the arithmetic needs. A200 kcd/m簡 practical at a daylight EV100 of 14.8 is 5.8 in exposed units ??about 5 stops over midgrey ??and against the default 4-stop threshold that is an excess of 3.0, of which the rays carryhalf a percent, spread over a couple of thousand pixels: roughly **fifteen stops under mid grey**.That is not a bug. **1? physical on a daylight-exposed 200 kcd/m簡 source is faint by nature** ??nobody sees a sunstar off a desk lamp at noon. The *same lamp at a night exposure* is anothermatter entirely: the pre-exposure is ten stops larger, the excess is enormous, and the star isthere at 1? with nothing added. So is the sun, which is four decades brighter again. The gain isfor the cases in between, and for the ones you simply want louder; the pattern's shape, falloffand dispersion are the pupil's at every setting. To see rays off an ordinary daylight practical,try **130??50**. Details and the alternatives considered: `scene-notes/decisions/s7-glare-gain.md`.What that buys, none of it authored:- **Ray count is the pupil's, not a formula.** 8 blades -> 8 rays, 3 -> 6, 9 -> 18, with the  real relative intensities. There is no clamp, because nothing is drawing lines. More blades  therefore means THINNER and FAINTER rays, not a brighter star: the same diffracted energy is  divided among more of them (energy per ray ~ 1/N, and an odd blade count makes 2N of them).  That is the physics, not a shortfall.- **No f-number ramp, and none wanted.** The pattern's size on the sensor is  `s = lambda * N * d / L`: stopping down spreads the SAME energy fraction over a proportionally  larger pattern. Rays get longer and dimmer per pixel as N grows, and wide open they are short  enough to hide under the source's own bloom. That IS "sunstars appear when you stop down".  The component's Analytic f-number ramp does not gate this model either ??in Wave mode the pass  is live at every aperture, so nothing pops in at f/6.4.- **Wide open there are no rays at all, because there is no polygon.** The blades retract into  the round barrel, and at `Maximum Aperture` they are flush with it: the pupil is the barrel's  circle, and a circle diffracts into rings. The iris polygon only emerges from the barrel as  you stop down (below `p = N_open/N ??cos(pi/n)` it is clear of it entirely), and the rays come  out with it. That is the other half of "sunstars appear when you stop down".- **Blade Curvature shortens and softens the rays** ??a rounded outline has less straight edge  to diffract off ??and **a shape mask throws its own pattern**, turning with `Mask Rotation`.- **The rainbow is dispersion.** Six wavelengths (420-670 nm), each a scaled copy  `PSF_l(u) = (l0/l)^2 PSF_l0(u l0/l)`: blue compact near the core, red out at the tips.  `Streak Dispersion` collapses them onto 550 nm for a white pattern.The FFT resolves the pattern's **structure** but not its **reach** ??the whole texture spansonly some tens of pixels on screen. Past its edge the kernel is extrapolated by theedge-diffraction law `I_ring(theta) * (R_tex / u)^2`, exact for a straight edge and pessimisticfor anything smoother, so the tail is never brighter than the physics allows. `Streak Reach` iswhere that tail is cut off ??and, since the pass moved to half resolution, it is also **the costdial**: the sprite is twice as wide in pixels as it was and there are four times as manycandidate source cells, so if a scene gets slow, pull `Streak Reach` first.The kernel depends only on the pupil's **shape**, so it is rebuilt on a **job** (10-30 ms, neveron the render thread, one in flight, the previous kernel stays live meanwhile) and only whenblades, the polygon exponent, either rotation, the mask, the mask scale or the sphericalaberration actually change. The f-number does **not** trigger a rebuild; it only scales theresult. Each rebuild logs its parameters, the core fraction, the physical glare fraction(`1 - core`) and the job's time; the glare pass logs the fraction it actually deposits.Known limits: the pupil is the **on-axis** one, so the corners do not get their cat-eye-clippedstars; the convolution is shift-invariant; and a shape change takes a frame or two to appear.The kernel lives in the depth of field stage (that is where the pupil is resolved), so Waveneeds `r_dof > 0`; until the first kernel lands the analytic lines carry the effect. Full modelin [DiffractionKernelSpec.md](DiffractionKernelSpec.md).Cvars: `r_HDRDiffractionKernel` (0 = kill switch, falls back to Analytic),`r_HDRDiffractionDebug`, `r_HDRDiffractionKernelSize`, `r_HDRDiffractionSAWaves`.### Analytic (the older model, kept)Light bends around the straight edge of every iris blade, and each edge throws a pair of rays:- **Even blade count**: opposing rays overlap -> **N rays**. **Odd count**: offset -> **2N**.  The ray count is clamped to [4, 24] (the renderer draws them as 12 symmetric line passes at  most, each painting two opposed spikes).- Brightness: `amount = ((N - 6.3) / (11 - 6.3))^1.2`, clamped 0-1 ??nothing below f/6.3,  **saturated by f/11**, after which stopping down reads as the rays growing rather than  brightening.- Length: `length = (N - 7) / (22 - 7)`, clamped 0-1 ??the **length curve owns f/7 to f/22**.- `Blade Rotation` goes straight into `HDR_Streaks_Angle` (and into the bokeh polygon's  rotation).These are the `HDR_Streaks_*` post effect params; an unmodified renderer does not know them(reads return 0, writes are silently dropped), so the effect needs this renderer/shader set.The ramp and the falloff here were tuned by eye; they are an approximation of what the wavemodel computes. Those copies land on the line from the source through the frame centreand out the other side, growing along the chain, each tinted by the coating that reflected it.Modern multi-coated glass shows them faintly, vintage and anamorphic glass shows them boldly,and moving the camera so the source crosses the centre makes the whole chain cross backthrough it.This is screen-space, not light-entity flares: anything bright enough - a practical lamp, anemissive surface, a hot reflection - throws a chain, and it reads the true pupil shape. Thatcomes for free, because a ghost is an image of the aperture and so is a bokeh sprite: therenderer draws the ghosts with the **same pixel shader as the sprite bokeh splat**, only adifferent vertex shader, so they carry the iris polygon, the shape mask and its rotation, theanamorphic oval, the cat-eye clip and the axial chromatic rim without a line of their own, andthey shrink with the iris the way the pupil does. Being formed inside the lens, they are neitherblurred by the depth of field nor cut by an in-focus foreground, and they still draw with thesprite bokeh turned off (`r_DepthOfFieldMode 1`). A ghost is also not a light source: it iscomposited into the frame after the glare family has taken its sources, so a ghost never growsdiffraction streaks, an anamorphic flare or a filter star of its own - a flare off asecond-order reflection would be a third-order one, and there is nothing there to see. One property, `Squeeze Factor` (S), drives three physically distinctconsequences, each on its own path through the renderer.**1. Field of view and the gate mask.** The projected (desqueezed) format is`sensorWidth * S` by `sensorHeight`, so its aspect is `formatAspect = sensorWidth * S / sensorHeight`(36 x 24 mm at S = 2 gives 3.0:1). When that format is wider than the viewport, the format's*width* is what has to fit: the horizontal field of view comes from the widened capture and thevertical field is derived through the viewport aspect, with black bars taking the rest.```hFOV = 2 atan(sensorWidth * S / 2f)vFOV = 2 atan(tan(hFOV / 2) / viewportAspect)      // formatAspect > viewportAspectvFOV = 2 atan(sensorHeight / 2f)                   // otherwise (spherical, or the format fits)```The bars are drawn in the final composite from the `r_LensLetterbox` cvar, which the componentpushes (and restores) exactly like `r_LensDistortion`: `formatAspect` when the mask is needed,0 otherwise. They are hard-edged, as a real gate mask is. At S = 1 nothing changes.**Show Squeezed Frame** swaps the presentation for the raw anamorphic negative: the same bandthe gate mask would keep is stretched vertically to fill the viewport (`r_LensLetterbox` goesnegative), so the whole picture carries the squeeze - circles become tall ovals, faces go thin -not just the bokeh. The camera frustum is identical in both presentations; switching betweenthem changes nothing about what is in frame, only how the band is shown.**2. Oval bokeh.** The pupil image is compressed horizontally by the same factor, so anout-of-focus point spreads into a vertical oval of `height : width = S : 1`. The gather kerneldivides every finished tap's horizontal component by S (both the polygon and the shape-maskkernels go through this), and the sprite bokeh splat narrows its quad the same way, dividingthe energy-conserving deposit by the oval's real area so brightness is unchanged.**3. Horizontal flare.** The cylindrical front element throws one long tinted line across theframe instead of a star. It is a separate effect on its own switch (`Horizontal Flare`), withits own threshold and its own single horizontal march of three widening iterations - eight tapseach, so `8^3` tap distances span the whole frame width. It follows the *opposite* f-numbercurve to the iris diffraction: strongest with the whole element in the light path and gone byf/11.```wideOpenness = clamp((11 - N) / (11 - 2), 0, 1)     // 1 at f/2 and wider, 0 at f/11amount       = HorizontalFlare * wideOpenness```The flare is pushed whenever the camera drives the render state, regardless of`Enable Diffraction Streaks` - one is a property of the iris, the other of the front element.Both ride the `HDR_Streaks_*` post effect params into the bloom target.---## HalationOn film, light from a very bright source does not stop at the emulsion. It passes through,reflects off the film base and re-exposes the emulsion from behind, in a halo far wider thanthe source itself. In a colour negative the red-sensitive layer sits deepest, so what comesback is red-orange, its edge is soft, and it only appears around sources that genuinely**overload** the emulsion - never around a merely bright sky.Halation is a property of the **film stock**, not of the lens. Unlike the diffraction streaksand the anamorphic flare, nothing here is modulated by the f-number: the four properties arepushed to the renderer exactly as authored, every frame, the same way the streak params are.The pass chain lives in `CBloomStage::ExecuteHalation()`, in the **bloom domain** - it runsright after the streaks, reuses the two quarter-resolution HDR scratch targets they leavefree, and blends into `$HDRFinalBloom` with the same bloom-weight compensation, so it costs nopermanent memory and needs no second tone-map hook:1. **Threshold** the half-res HDR scene at `Halation Threshold` with a soft knee of a quarter   of the threshold (the `HDRStreakThreshold` technique).2. **Spread** it wide, horizontally then vertically, through `HDRStreakStretch` with an   isotropic direction, a stride of `2 + 10 * radius` quarter-res texels and a near-flat per   tap decay of 0.90. This is what sets the halo's width: at radius 0.5 the 7 taps per side   reach 49 texels, about 196 full-res pixels on a 1080p frame.3. **Round** the profile with two `CGaussianBlurPass` passes at distribution `3 + 5 * radius`.   That utility's 16 bilinear taps are pinned to +-8 texels whatever the distribution, so it   cannot widen anything - it only smears the discrete tap gaps into a continuous soft edge.4. **Composite** into the bloom target with the stretch shader at a **zero** step (every tap   lands on the same texel, so the normalised sum is a plain tinted sample), tinted by   `Halation Tint` and scaled by `amount * 8 / bloomCompositeWeight`. The x8 gain is there   because an energy-conserving blur spreads a source over thousands of texels: without it the   halo is physically right and visually invisible.These are the `HDR_Halation_*` post effect params; an unmodified renderer does not know them(reads return 0, writes are silently dropped), so the effect needs this renderer/shader set.Master cvar: `r_HDRHalation` (**2 = diagnostic force mode**: amount 1, threshold 0.5, radius0.7, independent of the game-side params).---## Front filter PSFA cross-screen / star filter is a plate of etched grooves mounted in **front** of the lens.Every bright point in the frame is diffracted into lines perpendicular to the grooves: 4, 6 or8 points depending on the plate, at whatever angle the plate is turned to, at **every**f-number - unlike the iris sunstars, which need a stopped-down aperture - with rainbowdispersion toward the line ends. Brighter sources show longer lines not because the patternchanges, but because more of its faint tail rises above the scene.That last sentence is the whole model: a front filter is a fixed **point spread function**,and the picture is the scene convolved with it. The PSF is authored as an RGB texture, the waythe bokeh shape mask is, so the same mechanism covers any other front-element PSF a preset maywant (a smeared or dirty filter, a custom flare plate); the star filter is only its first user.With nothing bound, a procedural N-point star with rainbow tips stands in, so the effect istestable and has a sane default.The convolution is done **sparsely**, in `CBloomStage::ExecuteFilterPSF()`, right after thestreaks and in the same window where both quarter-resolution HDR scratch targets are free:1. **Threshold** the half-res HDR scene at `Star Threshold` with a soft knee of a quarter of   the threshold (the `HDRStreakThreshold` technique the streaks and the halation share).   Skipped entirely at amount 0 - off means no pass, not a pass depositing zero.2. **One sprite per bright quarter-res texel** (`HDRFilterPSF`): a procedural triangle list   expanded from `SV_VertexID` with no vertex stream at all, six vertices per grid cell. The   vertex shader reads its own texel, collapses the quad when nothing survived the threshold -   which is what keeps the cost proportional to the number of bright sources rather than to   the frame area - and otherwise expands a quad of `Star Size * frame height`, carrying the   texel's excess energy. The pixel shader rotates the quad-local coordinate by the plate's   angle and samples the PSF image (or the procedural star) through it.3. **Composite** additively into `$HDRFinalBloom` with the same bloom-weight divide the   streaks and the halation use, so the star's on-screen brightness does not move when the   scene's TOD bloom amount does. The deposit is divided by the sprite **area**, which is what   makes this a convolution rather than a glow: a wider plate spreads the same energy further   instead of getting brighter.The plate sits in front of the anamorphic element, so its pattern is squeezed horizontallyalong with the rest of the picture (read from `Dof_User_AnamorphicSqueeze` - one knob, not twothat can drift). It is **not** rotated by the iris phase and **not** scaled by the aperture: itis a plate, not the iris.These are the `HDR_Filter_*` post effect params, owned by `CHDRStreaks` because they are all"what the front of the lens does to a point"; an unmodified renderer does not know them.Master cvar: `r_HDRStreaks` (0 disables the whole streak / flare / PSF block; **2 does not**force the filter on - the plate is separate kit from the iris, and forcing it would hidewhether the params arrive).
